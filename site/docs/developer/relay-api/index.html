Relay server API

The relay server's HTTP routes: files, the Marketplace, feedback and the rest.

The relay is mostly two WebSockets, the hub and the pairing relay. Beside them it answers a small set of plain HTTP routes: a circle's sealed files, the plugin Marketplace, feedback, bounties, the pages that link a handle, and, where it is given the folder, the app built for a browser. This page lists every one. Relays that talk to each other, home records and a call's media relay have no HTTP routes of their own: they are spoken over the hub's socket. The public relay is at https://gogho.st. Anyone can run their own from the source: dart run relay/bin/relay.dart --port 8787. The WebSocket protocols are on The hub and pairing protocols, and a Postman collection of these routes is on API overview and Postman.

Conventions

  • CORS for one address, on two routes. These routes are for the app and for scripts, not for a page in a browser on another site: the relay sets no Access-Control-* header, but for the two things the app in a browser sends from an address of its own, POST /feedback and POST /market/abuse. A relay set with that address (GHOST_APP_ORIGIN) answers both with Vary: Origin, and, to a request whose Origin is exactly that address, with Access-Control-Allow-Origin naming it. An OPTIONS from that origin is answered 204 with Access-Control-Allow-Methods: POST, Access-Control-Allow-Headers: content-type, x-ghost-key, x-ghost-time, x-ghost-sig, x-ghost-body-sha256, x-ghost-body-length and Access-Control-Max-Age: 600. No other route, and no other origin, is told anything.
  • No match is not an error. A request that fits no route, whatever its method, answers 200 with the plain text Ghost Messaging relay. There is no separate health route: this is it.
  • JSON answers are application/json; charset=utf-8. Request bodies are read as UTF-8 JSON or raw bytes; no Content-Type is looked at.
  • Hex is lowercase. Ids and hashes in paths must match their shape exactly, or the route does not exist.
  • Times are whole milliseconds since 1970, as decimal digits.
  • Per-address limits on these routes go by the first value of X-Forwarded-For, or the connection's address where there is none. The hub counts differently: see Signing in to the hub.

Each module says no in its own shape:

ModuleA refusalNotes
Files{"err": "No such space."}A sentence. A few carry more: have, done, seq.
Feedback{"error": "Feedback is sent with POST."}A sentence, under error, not err.
Marketplace{"ok": false, "error": "not_found", "message": "There's nothing here by that name."}error is a fixed code; message is for people. Every success carries "ok": true.

Outside the modules, a path or a query whose percent-escapes are not UTF-8 answers 400 with no body, and an error nothing else caught answers 500 with no body. Both close the connection.

Signing a request

Writes to Files, feedback, and most of the Marketplace are signed with the install's own key, the same one the hub knows it by. No account or password is involved. A bounty is signed the same way, by one key the relay was given.

ThingFormat
KeyP-256 (secp256r1). The public key is 33 bytes compressed: 02 or 03, then x. In a header it is standard base64 with padding, 44 characters.
SignatureECDSA over the SHA-256 of the signed string. 64 bytes: r (32, big-endian) then s (32). Not DER. Standard base64, 88 characters.
IdThe first 16 bytes of the SHA-256 of the 33 key bytes, as 32 lowercase hex digits. This is who the relay says wrote something.
Body hashSHA-256 of the body's bytes, 64 lowercase hex digits. For an empty body: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855.

All three modules take the same three headers and sign five lines joined by a line feed (\n), as UTF-8, with no line feed after the last. Only the first line and a few rules differ.

x-ghost-key:  <base64 of the 33-byte public key>
x-ghost-time: <milliseconds since 1970>
x-ghost-sig:  <base64 of the 64-byte signature>

The relay remembers what each key signed, so the same request sent twice is refused the second time. To try again, sign again with a new time.

Files

Every Files route but GET /files also carries the space's token: Authorization: Ghost <token>, 64 lowercase hex digits. Reads need only the token. Writes need the token and the signature.

ghost-files v1
<METHOD>
<path and query, as sent>
<time>
<body sha256 hex>
  • The third line is the whole request target, query included: /files/0123456789abcdef0123456789abcdef/log?after=7.
  • The time may be up to 10 minutes from the relay's clock, either way.
  • Where the body is not read (DELETE /files/{space}, POST …/done), sign the empty body's hash.
  • For a blob's piece sent with x-ghost-body-sha256, the last line is that header's value, and the signature is checked before the body is read.
  • Any failure answers 401 {"err": "Bad signature."}.

Marketplace

ghost-market v1
<METHOD>
<path>
<time>
<body sha256 hex>
  • The third line is the path alone. A signed request with any query string is refused.
  • The time may be up to 5 minutes from the relay's clock.
  • A POST must say its body up front, in two more headers: x-ghost-body-sha256 (64 lowercase hex digits; the last signed line) and x-ghost-body-length (the length in bytes, equal to Content-Length). A chunked body is refused.
  • A GET or DELETE must send neither of those headers and no body, and signs the empty body's hash.
  • A missing header answers 401 unsigned. A bad key, time or signature, or a repeat, answers 401 bad_signature. A broken shape (a query, a header sent twice, a length that does not match) answers 400 bad_request.

Signatures inside Marketplace bodies

Review's decisions are signed a second time, by the reviewer's key, so that the apps can check them without trusting the relay. Each is the same kind of signature over lines joined by \n, and travels as a JSON object with exactly the fields shown. Here key and sig are strict base64: the standard alphabet, padded, no whitespace.

Sign-in links

These are pages for a browser, not an API to call. When someone links a Discord, Telegram or X handle, the app asks the hub for a sign-in address and opens it. The address holds a state made for that install, good for 10 minutes and for one sign-in. The relay checks the sign-in with the network, links the handle, and tells the install over the hub. A network whose keys are not set on the server is off, and its page says the link is no good.

Starts a sign-in the app asked for over the hub. Sends the browser to the network's own sign-in (Discord, X) or shows Telegram's login widget.

Files

A space's files live on the relay as sealed blobs, beside an ordered log of sealed operations that says what the files are. The relay can't read either: names, keys and contents are sealed by the apps. It sees the space's id, each blob's size, when things were written, and the id of the install that wrote them.

A space is named by an id (32 hex digits) and guarded by a token (64 hex digits), both made by the apps from the space's secret. The relay keeps only the token's hash, and a wrong token is answered exactly as a space that isn't there. Anyone with the token can read. Writing also takes a signature, so a blob is written and finished only by whoever started it, and removed by them, the space's owner, or a moderator who shows the space's signed roster.

Uploading a file is three steps: reserve a blob with its size, send its pieces in order, then finish it. An upload cut short carries on from have. A blob not finished holds its room in the space until it is finished or dropped, and the space's state lists the newest hundred of them under parts, so an app can show an upload that stopped halfway and carry it on or remove it.

Feedback

The app's Share feedback sends one signed report. The relay files it on the server's feedback board and answers with the ticket's id. It keeps nothing itself. A username in the report is filed as given when the signing key holds that username, and marked not verified otherwise. On a relay with no board set up the route answers 503.

Limits: 5 reports an hour and 20 a day from one install, 300 a day from everyone, 10 MiB a report, three screenshots of 3 MiB each.

Marketplace

The Marketplace holds plugins from other developers and the queue they wait in for review. A plugin's package is one JSON file in the ghost-plugin/1 format, sent in canonical form (keys sorted, no whitespace) and named by its SHA-256.

Anyone can read the catalog, the withdrawals list, approved packages and listed screenshots. A developer signs with the key that holds the username in the plugin's developer field. Review is an install that holds one of the relay's admin usernames and signed in to the admin page over the hub in the last 8 hours, or the last 30 minutes for approving, revoking, blocking and listing. No password travels over these routes.

The relay is not trusted with a plugin. An approval is the reviewer's own signature over the plugin's id, version and hash, and the app checks it against review keys it already knows before it adds anything. The catalog carries no names or pictures: the app fetches each package and reads them from it.

The relay keeps packages, screenshots, submissions with their notes, reports, and a log of what review did. A report is kept without its sender's key.

The same review takes reports of people and messages (/market/abuse). The app seals each one to the review keys before it sends it, so the relay holds an envelope it can't read, and never who sent it. It keeps the newest 150, letting go first of the oldest one marked done.

Sending souls

A person can send some of their souls to someone else on the same relay. The sender signs a POST /souls/send with their own hub key, so the relay knows whose souls to move: the id of the key that signed. The headers are the three a bounty carries, over the five lines ghost-souls v1, POST, the path, the time and the body's SHA-256 in hex.

Souls only move. The sender's count goes down and the receiver's goes up by the same number in one step, with a receipt, and all three are written to disk together before the relay answers. The receiver must hold a username on this relay, so souls can't be sent to nobody. Both people are told their new count over the hub if they are connected.

Each sending carries an id the sender makes up. The relay moves souls once for an id: a request sent again because its answer was lost gets the first receipt back with "again": true. The app writes that id into the card it puts in the chat, and the other person's app asks POST /souls/receipt before it shows the card as souls sent. A receipt is given only to the two people in it.

Limits: 1 to 100 souls at a time; 300 souls and 10 sendings from one person in 24 hours; 20 askings to send and 300 receipt checks an hour by one key; 600 signed requests an hour from one address; a body of 1,024 bytes. Receipts are kept for a day at least, and the newest 5,000 after that.

Every answer of these two routes is JSON with ok. A relay from before them answers the paths as it answers any it doesn't know, with 200 and a line of text, and the app reads that as "not available yet".

The app in a browser

A relay started with --web <folder> serves the app built for a browser under /app/, as plain files. A page in a browser may speak only to where it came from, and the hub sends no CORS headers, so the page and the hub have to be one address: this is how a relay gives its people the app in a browser. Without the folder there is no /app/, and these paths get the root answer.

  • GET and HEAD only. Nothing is written or kept about who asked.
  • Only files inside the folder, links followed. A folder is never listed.
  • index.html, and any file whose name does not hold a hash of its contents, answers Cache-Control: no-cache with an ETag. A name with eight or more hex digits between dots before its ending (main.dart.3f9a1c2b.js) answers public, max-age=31536000, immutable.
  • Nothing is compressed as it is asked for. A .br or .gz copy beside a file, no older than it, is sent where Accept-Encoding takes it.
  • Every answer carries the page's own Content-Security-Policy (read from its <meta>, with frame-ancestors 'none' added), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, Cross-Origin-Opener-Policy: same-origin, Cross-Origin-Resource-Policy: same-origin and Permissions-Policy: camera=(), microphone=(), geolocation=(), display-capture=(). HSTS is left to the web server in front.

Running your own

The relay is one Dart program with no dependencies beyond Dart's own library. It listens over plain HTTP on this machine alone unless told otherwise, so on a server it sits behind a web server that holds the certificate.

dart run relay/bin/relay.dart [--host 127.0.0.1] [--port 8787] [--data relay-data] [--web <folder>] [--verbose]
FlagDefaultMeaning
--host <address>127.0.0.1Where to listen.
--port <number>$PORT, else 8787The port.
--data <folder>relay-dataWhere everything it keeps is written.
--web <folder>$GHOST_WEB_DIR, else noneThe folder flutter build web made, served under /app/.
--verboseoffSays when an install joins or leaves. Never an address, never a whole id.
--help, -hPrints the flags.

GHOST_MARKET_*The Marketplace's switch, limits and review keys.GHOST_MARKET_ON (1; 0 turns it off), GHOST_MARKET_REVIEW_KEYS (a comma list of review keys in base64; empty takes the signed-in admin's own key), GHOST_MARKET_NEED_VERIFIED (0), GHOST_MARKET_NAME_AGE_DAYS (7), GHOST_MARKET_MAX_PACKAGE (262144), GHOST_MARKET_TOTAL (1 GiB on disk), GHOST_MARKET_REPORTS_A_DAY (500: what installs with no verified number or linked account may report in a day, all together).
The app only trusts review keys it knows

Your own relay can run a Marketplace, but the app adds a plugin only when its approval is signed by a review key the app was built with. Approvals from your relay's reviewers mean nothing to an unchanged app.

A relay that links with others makes a key of its own the first time it starts, relay-key.json in the data folder, readable by its own user alone. Its name to other relays is made from that key: keep the file, and keep it private.

The full list of variables, with each one's least and most, is in the source: relay/lib/files.dart, relay/lib/market.dart, relay/lib/handles.dart, relay/lib/feedback.dart, relay/lib/pushes.dart, relay/lib/federation.dart, relay/lib/turn.dart, relay/lib/ws_door.dart and relay/bin/relay.dart.
